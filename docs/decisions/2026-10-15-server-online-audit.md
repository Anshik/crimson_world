# Сервер и сетевой интерфейс: read-only аудит

Проверка 15 октября 2026 после появления `server/` и `game/online.js`. Пункты ниже требуют исправления перед публикацией.

## Критично

- `server/core.py:29,154-156`: сервер заранее передаёт в QuickJS числа `1..6`, но движок иногда просит d4, d13 или другое число граней. Это может дать ошибку в бою/защите и ограничивает городскую колоду шестью картами. Источник случайности должен генерировать значение с учётом фактического `sides` каждого вызова, включая d13.
- `server/core.py:130-135`: сессия не имеет срока действия. Любой найденный cookie остаётся рабочим, потому что `last_seen` только обновляется. Ввести абсолютный или скользящий TTL с удалением/отказом для просроченных записей; cookie TTL сам по себе недостаточен.
- `server/core.py:143-159`: после команды результат не прогоняется через `rules.validate`. Команды работают с серверным состоянием, но защитная проверка должна выполняться до записи результата; особенно после добавления новых методов.
- `server/core.py:31-32` и `server/app.py:62-69`: `createCharacter` не проверяет, что персонаж создаётся один раз. Повторная команда может перезаписать прогресс и пересоздать героя. Разрешать её только для незаполненной legacy-анкеты либо сделать отдельным одноразовым переходом.
- `server/app.py:141-169`: обмен вручную меняет поля героя и не проверяет результат через `rules.validate`/`equipment.validate`. Передача находки, надетой в кольцо, оставляет у отправителя пустое владение при занятом слоте; передача оружия/щита/артефакта требует синхронизации экипировки и derived stats. Добавить проверку всех передаваемых объектов до мутации и валидацию обеих партий перед коммитом.
- `server/app.py:161-166`: таблица `unique_items` обновляется, но не является проверкой единственности. Принимать артефакт следует только после проверки `item_id` в этой таблице и состояния обеих партий в одной транзакции; `INSERT OR REPLACE` не должен маскировать дубликат.

## Важно

- `server/app.py:112-124,141-160`: `int()` для количества монет/предметов и JSON payload могут выбросить `ValueError` внутри обработчика и дать 500. Нужны строгая схема payload, положительные целые количества и лимиты до записи предложения.
- `server/app.py:112-121`: предложение проверяет общую клетку при создании, но не запоминает ревизии. Повторная проверка при принятии есть, однако полезно истекать старые открытые предложения и проверять типы/лимиты в обеих фазах.
- `server/app.py:104-110`: обратная связь не ограничена по частоте. Добавить небольшой rate limit на пользователя/IP, сохранив допустимый авторский текст и мат.
- `game/online.js:10-47`: интерфейс показывает все комбинации расы и происхождения и ждёт отказ сервера для несовместимых вариантов. Фильтровать происхождения по `TOVILIS_CHARACTERS.races[race].origins` и использовать единый экспорт описаний; сейчас подписи расходятся с `characters.js` (`Алый Дракон`, `Семь Шахт`, `Гномьи земли`).
- `game/online.js:63-67`: клиент сериализует `method/args/revision`, что хорошо для CAS, но нельзя считать `state` клиента источником. При конфликте перезагрузка через `/api/me` должна быть единственным восстановлением.

## Что уже соответствует цели

Состояние хранится в SQLite, `BEGIN IMMEDIATE` используется для команд и принятия обмена, idempotency-команды проверяют `command_id` и хэш запроса, внешняя запись dice не принимается, CSRF проверяется для изменяющих запросов, а общий город отдаёт только presence без email. Эти свойства сохранять при исправлениях.
