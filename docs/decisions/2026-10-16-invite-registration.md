# Регистрация по приглашениям

Дата: 16 октября 2026 года. Статус: принятое правило первой серверной версии; детали безопасности — обязательный контракт перед публичным пилотом.

## Действующий пользовательский поток

Пользователь регистрируется по одноразовому коду приглашения, имени пользователя и паролю. Email не входит в регистрацию, профиль или публичный API; старое значение сохраняется только как совместимый алиас входа уже существующего аккаунта. Никакой новый аккаунт не должен зависеть от почты. Общий предел — десять аккаунтов; один производственный аккаунт уже занят, значит первому пилоту выдаётся девять приглашений.

Имя нормализуется через Unicode NFKC и `casefold`; та же нормализация используется при входе. Старый email-алиас сохраняется при миграции и продолжает работать только для входа старого аккаунта. Регистрация без приглашения, по старому email или обходом лимита запрещена.

## Контракт приглашения

Оператор создаёт приглашение только через защищённый серверный CLI. В базу попадает хеш кода, а сырой код выводится один раз и передаётся игроку вне HTTP-журналов. Приглашение имеет срок действия и может быть отозвано. Проверка, создание пользователя и пометка приглашения использованным выполняются атомарно; повторное использование и параллельная гонка дают отказ. Внешний путь приглашения не должен раскрывать код в URL или логах.

Операционные команды описаны в [инструкции по размещению](../DEPLOYMENT.md#регистрация-и-приглашения). Команды выдачи, списка и отзыва не являются пользовательским HTTP API.

## Разбор ссылки приглашения

Строка приглашения после `#invite=` разбирается по длине полного префикса, поэтому разделитель `=` не попадает в код. Пользователь может вставить целиком ссылку из адресной строки; ранее открытая форма со старым значением `=code` также принимается сервером. Это не меняет хеширование и одноразовость приглашения.

## Миграция и восстановление

Переход старой таблицы пользователей с обязательным email на nullable должен выполнять SQLite-пересборку таблицы с `PRAGMA foreign_keys=OFF` только на время миграции, сохраняя все исходные `users.id` и проверяя ссылки всех дочерних таблиц до включения внешних ключей обратно. Нельзя удалять или пересоздавать дочерние строки и нельзя добавлять каскадное удаление, которое изменит историческое поведение.

Смена пароля администратором требует одноразового истекающего хеша, а после успешной смены все активные сессии пользователя должны быть отозваны. Почтового восстановления нет; восстановление выполняется только через защищённую административную процедуру.

## Исключённая интеграция

16 октября почтовая регистрация и интеграция с внешним отправителем исключены из пилота. Не добавлять настройки, токены, формы или обещания отправки писем без отдельного решения владельца.
